# 020：两位开发者怎样并行而不互相覆盖

本教程教A与B完成一次小任务交接，配套规则见[计划008](../plans/008-parallel-development.md)。A负责美术/UI/粒子/声音表现；B负责玩法创新、实验室与集成协调。用户始终是仓库owner，可能兼任A，但最终审阅/merge决定权不随A/B角色分配转移，A和B都没有因角色而获得长期合并授权。

## 1. 开工先确认“哪台电脑、哪份工程”

新会话、恢复或换电脑时，先只读检查主机名、OS、当前用户和目录，再核验本机Git与Godot。Windows PowerShell可分步运行：

```powershell
hostname
[System.Environment]::OSVersion.VersionString
whoami
Get-Location
git --version
Get-Command git -ErrorAction SilentlyContinue
```

Godot不一定在PATH里。找到本机实际可执行文件后运行`--version`，确认是固定的4.7.1 stable标准版。不要复制另一台电脑的绝对路径或把“以前装过”当成当前事实。

按AGENTS顺序读README、PROJECT、STATUS、FILE_MAP、CONTRIBUTING、REVIEW及当前教程。检查已有修改和Git基线：

```text
git status --short --branch
git log -5 --oneline
git remote -v
```

看到`project.godot`或其它已有修改先保留，查明来源。不能用`reset --hard`或覆盖配置让工作树看起来干净。两人各用独立checkout，不能把同一个实时工程目录通过同步盘同时编辑；Godot缓存、凭据和个人MCP配置不共享。

## 2. 先写小任务卡和整文件边界

任务卡最少写清：要解决什么、如何判断完成、允许改哪些文件、哪些文件要B接线、当前基线SHA、谁实现/谁独立审查。不要只写“A做美术、B做玩法”，因为当前actor脚本里绘制和规则还在一起。

例如A做新的生命面板样板，先交独立面板与显示需求；当前`run_hud.gd/.tscn`、`run_arena.gd`仍由B单写。A若需要修改这些文件，先让B冻结并交接整个文件，完成后再交回。不能约定“一个人改上半段、另一个人改下半段”。

未来拟建的`presentation/`目录供A写表现，实验室目录供B写试验；两者当前都不是已落成的模块。先完成一个实际需要的接口拆分，再以新目录实现并行，避免一边宣布隔离、一边继续同时改`enemy.gd`。

## 3. 从同一基线分支

B先把准备采用的已验证主线SHA写到任务卡；A/B各自检查该SHA一致，再各开分支。独立checkout且无待处理修改时，常规流程为：

```text
git fetch origin
git switch main
git pull --ff-only
git rev-parse HEAD
git switch -c feat/presentation-sample
```

B另用`feat/gameplay-lab`。这些是示例名，遵循[CONTRIBUTING](../../CONTRIBUTING.md)的`feat/`约定，不是已执行的操作。如果拉取后HEAD与任务卡不一致，先重新核对共同基线，不能分别从“各自最新”继续。已有修改时先由作者决定保留方式，或在另一个干净checkout开工，不机械照抄切分支命令。

## 4. 数据、事件和请求各做一件事

S1拟定接口后，A才能放心换表现；以下是契约示意，不能照抄成对当前代码已存在的API：

```text
玩法 → 显示数据：entity_id、hp、max_hp、team、cooldown、stage
玩法 → 表现事件：hit(point, strength, run_revision)、died、picked_up
面板 → 玩法请求：request_purchase(item_id, quote_revision)
```

数据回答“现在显示什么”；事件回答“刚发生什么”；请求回答“玩家想做什么”。生命、伤害、价格和有效交易由B的逻辑决定，A消费数据和事件并展示结果。按钮不直接扣币或写血量，B再次校验状态、版本、库存和余额后才处理请求。

A可改变颜色、形状绘制和粒子，不能顺手缩放刚体碰撞形状来让角色看起来更小。B改碰撞规则需提供对应数据/事件，不能把新伤害计算塞进动画回调。物理用力和冲量，复位用物理状态接口；接口拆分后要证明这些规则保持。

## 5. 按S0～S4推进，不跳过样板和机制选择

S0先一起跑共同基线。S1由B做必要的小范围接点拆分，A确认能消费。S2才并行：A做新战斗HUD和奖励/休息面板样板；B做实验室、开发预设及对照入口。

旧暖色样板已被用户否定，A不能把它当成默认认可方向全面替换。先展示新样板并收集反馈，再决定扩展。下一机制也没有被选定；三个命名候选是“借墙蓄能”“方向弱点”“交互场地”，均只在计划中。由用户选一个并给出验收，再进入S3实现一个机制对照，不一口气做完三个候选来代替选择。

实验室快捷键只在实验室响应；正式run仍按正常速度运行，不增加全局试验热键。调参保存成开发预设，默认不覆盖正式数值；共享预设需注明种子、初始构筑、参数、用途和恢复步骤。两份对照使用同样场景/种子，记录实际差别；夹具清怪或强制升级不能冒充真人通关。F5旧侧视入口、F6运行当前run、独立arena三靶场继续保留。

S4由B接线，独立审查者检查，用户作为owner最后审阅实际结果。实验有趣与否、视觉是否合适、音色是否刺耳都需要真实体验，自动检查只证明所覆盖的规则。

### A怎样交一项表现成果

按[计划008](../plans/008-parallel-development.md)的A1～A6任务表逐项交付：A1新视觉规范与样板，A2角色/场地辨识，A3战斗HUD，A4选择与流程面板，A5碰撞/伤害/粒子，A6声音及整套一致性。先在任务卡选一项，列独立交付文件、需要的数据显示/事件和B接线文件。A1样板给用户评价后再扩展，不直接覆盖正式场景。

例如做“敌人受伤反馈”：先明确有效伤害事件和当前/最大生命数据；在独立表现组件中展示闪白/粒子/数字；用固定生命变化证明表现正确，再交B连接真实事件。验收时检查无效擦碰不会显示掉血、颜色之外仍有数字或轮廓、关闭粒子仍能看懂。A自查这部分效果，B核对没有改变伤害/物理，用户评价最终观感；三者是不同证据。

### B怎样在实验室复现一次手感问题

以下是拟建实验室的操作约定，目前还没有对应按钮或快捷键。首版八个夹具为单敌、怪群、墙角、伙伴、范围、炮台、分裂、首领，逐一用现有机制实现；不能把本教程中的步骤当成现有功能说明。

1. 选择夹具和共同基线，保存原始开发预设，固定种子、起点、初始构筑、发射方向/力度。
2. 每次只改一个白名单参数。表现显隐/试听开关立即生效；发射物理、敌人参数、伤害/伙伴/分裂规则和夹具布局一律显示“待应用”，重置后生效。白名单和单位见计划008，首版不提供任意属性修改框。
3. 重置走物理接口，等待复位完成，再通过正式发射接口发一次相同冲量。若被冷却/暂停/状态阻塞，显示拒绝原因；不能强写速度绕过。
4. 对照速度、接触相对速度、链/代数、生命、本次实际伤害、冷却、有效/无效接触次数和清场时间。看逻辑端拒伤原因：攻击资格、复位/旧事件、目标状态、速度阈值、配对冷却、投射物资格、玩家无敌及实际范围。
5. 保存试验预设和一次复现记录，写清“原配置怎样、改了什么、预期/实际是什么、还有什么没查”，再决定保留参数还是恢复默认。未改善就回到目标，不以更大数字代替验证。

拒伤日志必须由实际判定分支输出，含时间、源/目标ID、链/世代、速度/阈值、结果；有界存储，同类可合并计数。没有原因的事件显示未知，不能根据粒子猜理由，也不能为记日志重复结算伤害。

首版预设记录schema、基线SHA、夹具ID、种子、白名单参数、构筑和固定发射请求。加载先校验并显示差异，再重建夹具；“恢复默认”恢复该夹具基准，不覆盖正式`.tres`。个人记录放忽略目录，经审查的共享开发预设才进入仓库。记录同时写设备/Godot版本、步骤、读数/日志、截图/录音及未测项，另一台电脑据此复现。

首版只做可靠的单次固定发射与记录；批量扫描、输入录制/回放、曲线时间线和统计导出留后续评估。建议lab专用键为`1～8`切夹具、`R`重置/应用、`T`固定发射、`L`显隐读数/日志、`Ctrl+S/O`保存/加载开发预设；实现时检查按键冲突，编辑输入框时不触发。正式run不接这些开发热键，也不改变正常时间倍率。

## 6. 每次交接交“可验证的结果”

把下面模板填进已有任务记录或PR。没有线上Issue/PR授权时先本地保存，不因模板存在就自动创建线上记录。

```text
目标/验收：
共同基线SHA / 本分支：
实现负责人 / 当前唯一写入者 / 独立审查者：
修改文件（含新增、删除、职责变更）：
需要B接线的现有共享文件：
数据/事件/requests变化及最小调用示例：
正式默认有无变化 / 开发预设与恢复方法：
验证：实际设备、Godot版本、命令、退出码、日志、观察结果：
真人试听/视觉/手感：已查项与未测项：
教程链接 / 用途清单 / 自动目录：
已知限制 / 阻塞 / 下一步：
本任务Git授权：commit、push、PR、merge分别有哪些明确授权：
```

例如声音交接应有实际试听事件与密集叠加观察；不能只填“音频测试通过”。UI交接给实际窗口尺寸和样板图；不能只填“节点存在”。玩法交接记录输入→规则→输出、边界和重开，不能只交一个按钮截图。

## 7. 合并文档，再生成目录

每个独立分支都更新自己的教程、STATUS和用途清单，并生成本分支目录。B集成时先逐条合并`docs/file_purposes.json`和STATUS的事实，再重生成`FILE_MAP.md`；不要手工拼接自动树或用ours/theirs丢掉另一方记录。两人若在同一checkout协作，这些共享文件也只能由登记的一个人写，另一人提供待合入文本。

核验本机Godot路径后，以任务变量保存该路径；下方第一行是提示，不是可原样运行的真实路径：

```powershell
$taskGodotExe = '<本机实际Godot可执行文件绝对路径>'
& $taskGodotExe --headless --path . --script tools/project_map.gd -- --write
& $taskGodotExe --headless --path . --script tools/project_map.gd -- --check
./tools/verify.ps1 -GodotExe $taskGodotExe
```

Windows图形版Godot可能提前返回，生成/检查目录时需要等进程实际完成并核对日志、退出码；可按`verify.ps1`的`Start-Process -Wait -WindowStyle Hidden`方式运行。完整验证入口已管理等待与输出，不能把刚启动进程当作测试成功。新增检查需同步本机入口和CI。

## 8. 最终Review、Git授权和用户审阅

开发中可以局部检查；只有开发者认为相关功能基本完成、准备提交时，才按[REVIEW](../REVIEW.md)发起完整最终Review。汇总代码/测试、教程、用途与目录，安排未参与实现的人或Agent独立只读审查。自查写“自查”，A或B参与实现后不能冒充该范围的独立审查者。

报告结果和未测项后按明确授权执行commit、push、PR。远端CI只能上传后核验；B可协调修复与复测，最终由用户作为owner审阅并决定merge。本轮用户明确授权当前批次PR和merge为一次例外，未来不得据此自动合并；条件式授权已满足时不反复要求相同确认，也不把“可以提交”扩大为“可以上传/建PR/合并”。用户若兼任A，这次审阅同时具有表现负责人和owner身份；将A工作交给别人不会转移owner权限。

常见卡点：同一文件冲突时先保留双方内容、明确当前写入者，再语义解决；接口不够时提出变更请求，不跨目录改对方逻辑；样板不认可先修改样板，不全面铺开；实验没有验证价值先回到目标，不因写了代码就强行集成。最终交接写清实际进入哪个阶段，计划文档完成不代表实验室、接口拆分或新机制已完成。
