# 每次改动的 Review

目标是尽早发现问题，确保代码、功能、教程和目录一起交付。保持小任务，不给每次改动增加一套庞大流程。

## 一个闭环

| 步骤 | 必须看什么 | 留下什么 |
| --- | --- | --- |
| 1. 开始 | 验收条件、工作区已有修改、相关模块与教程 | 本次范围和验证方式 |
| 2. 自查 | `git diff` 及新增文件；正确性、边界、资源释放、无关变更 | 发现的问题与修正 |
| 3. 功能测试 | 正常路径、失败路径、回归风险；适用的自动检查与人工试玩 | 实际命令、结果、未测项 |
| 4. 文档检查 | 教程是否讲清原理/改法；FILE_MAP 是否完整且用途准确；链接/配图是否可用 | 教程和目录入口 |
| 5. 独立 Review | 未参与实现的审查 Agent 或另一位成员检查上面四项 | 有文件位置与理由的问题清单 |
| 6. 修复复测 | 修复阻塞问题，重跑受影响检查，请审查者复核 | 已解决/保留问题和理由 |
| 7. 请求授权 | 向用户展示结果与精确的待提交范围 | commit 与 push 的明确选择 |

发现严重问题时立即回到实现，不需要等到最后。修改代码后，旧的“通过”不能代替新验证。

## 如何挑测试

- GDScript/场景/物理变化：运行 `tools/verify.ps1`，并按改动试玩正常与失败路径。测试 bug 修复时，优先补能复现原问题的回归测试。
- 工具/CI 变化：测试成功和失败情况，包括新增文件缺少用途、目录过期时能否拦住；复核 CI 命令与本机一致。
- 纯文档变化：检查引用、树与实物一致、图可阅读、规则没有矛盾。游戏行为未变时注明“不涉及游戏运行”，不为了清单虚写试玩。
- 暂时无法进行的跨系统、声音或手感验证：明确标注未测及影响，不能写成全部通过。

目录检查已接入 `verify.ps1` 和 GitHub `smoke`。工具可以发现文件漏写和目录过期，**不能判断教程是否好懂、文件用途是否写对**，这部分由审查者负责。

## 审查结果怎么写

按严重性列“必须修复 / 建议修改 / 仅供参考”，每条包含文件位置、问题、影响和建议。必须修复项解决后才能声明 Review 通过。建议项要处理或说明暂缓原因。不制造凑数问题，也不把“没有发现问题”说成绝对没有缺陷。

普通任务在完成汇报或 PR 记录即可；涉及工程流程、较大功能、复杂 bug 时，将结论保存在 `docs/reviews/日期-主题.md`。记录审查者、自查/独立审查的身份、审查范围、验证结果、问题处理和未测项。没有独立审查条件时如实说明，请用户安排，不能声称独立 Review 已完成。

## 提交前问用户

可使用：“Review 与适用测试已完成，教程和目录已同步。待提交文件为……；另有……是原有修改，不包含在内。是否只 commit，还是 commit 并 push？”

这一步的来源是用户要求，不是额外的自动审批机制。未收到明确回答时保留本地修改。commit、push、创建 PR、合并是不同动作；创建 PR 与合并同样需要明确授权。授权 push 后，CI 只能在上传后运行，应再检查远端结果，不能提前声称通过。
