# 两位开发者并行分工与下一阶段计划

日期：2026-10-31。本文把已讨论的协作分工写成可执行边界。它不表示表现接口、实验室或下一机制已经实现，也不替代[Git公约](../../CONTRIBUTING.md)与[最终Review](../REVIEW.md)。操作步骤见[教程020](../tutorials/020-parallel-workflow.md)。

## 目标与事实边界

让A能独立推进美术、UI和视听表现，让B能独立推进玩法试验，同时保持正式入口可玩、共享文件只有一位写入者，最终由用户作为仓库owner审阅并决定合并。用户可能兼任A；owner权限属于用户，不随A/B角色分配转移。

当前`player_ball.gd`、`companion_ball.gd`、`enemy.gd`、`boss.gd`、`rice_lure.gd`仍同时含机制和绘制；HUD与整局接线也有交叉。音频已有独立导演，但`impact_feedback.gd`仍共享碰撞视觉与兼容接口。不能因为口头分成“美术/玩法”就允许两人在同一个脚本上下半段同时改动。

已展示的暖色UI样板被用户否定，保留它仅为反馈记录，不作为A默认采用的方向。正式新视觉需另做样板并获得反馈。下一项玩法尚未选定；讨论中的三个候选均不是批准需求，本计划不替用户选中其中之一。

当前批次顺序为：先导出可运行Windows包给策划使用，再写清分工与计划，最后对本批明确范围完成Review、PR与合并。导出包的实际位置、启动证据和Git结果由当前交付记录填写；本文不提前声称已经完成。该包用于反馈，不把导出成品、个人设置或引擎缓存提交到仓库。

## 人员职责与授权

| 角色 | 主要工作 | 决策及权限边界 |
| --- | --- | --- |
| 用户：仓库owner，可兼任A | 决定方向、验收与Git授权，最终审阅集成结果 | 最终审阅/merge决定权不随A/B分工转移 |
| A：美术与表现负责人 | 美术方向、UI布局、图标、角色外观、粒子、声音设计与试听、视觉可读性 | 向用户提交表现样板；角色本身不附带merge权限，样板未认可前不全面替换 |
| B：玩法与集成协调 | 玩法创新方案、实验室、物理/战斗/经济/状态规则、接口拆分、共享接线、集成与回归 | 整理基线和接口、语义合并共享文档；协调不自动带来merge权限 |
| 策划/试玩者 | 体验Windows包，记录成长、难度、视听与操作反馈 | 反馈不自动授权线上Issue、采购素材或新机制开发 |

本轮用户已明确授权当前批次PR与merge，这是一次授权例外；在最终Review、适用测试及CI满足后按明确范围执行。未来A/B或其Agent不能引用本次授权自行merge，commit、push、PR、merge仍按每次任务的明确授权处理。用户已给出的条件式授权不重复索要；范围扩大后需重新核对授权。用户兼任A时可同时进行表现审阅与owner审阅，但这不意味着其他担任A的人自动继承仓库权限。

| 范围/现有文件 | 当前写入者 | A可并行交付什么 |
| --- | --- | --- |

| `run_director.gd`、`run_arena.gd`、`arena.gd`、`run.tscn`、`arena.tscn` | B | UI/声音/表现需要接入的接口与最短示例 |
| `run_hud.gd`、`run_hud.tscn`、`rest_panel.gd/.tscn` | B，直至明确完成拆分或交接 | 独立面板样板和可编辑资源；不直接覆盖正式HUD |
| `scripts/impact_feedback.gd`与公共音频事件接线 | B | 音色、事件映射、响度与并发听感反馈；未来独立表现组件 |
| `audio_director.gd`、`audio_palette.gd`及音频资源 | 每个任务先登记单一负责人；表现资源可明确交给A | A接管时B只提交接口变更请求，不能同时编辑事件表 |

| 未来独立`presentation/`目录 | A，目录尚未建立 | 可编辑视觉/UI/粒子/音频表现及样板，目录正式路径由S1接口拆分时确定 |
| 未来独立实验室场景/脚本/开发预设目录 | B，尚未建立 | A可提供样板演示场景，通过登记交给B集成 |
| 测试、`tools/verify.ps1`、CI配置、自动目录生成器 | B协调，任务中指定唯一写入者 | A提供视觉/试听检查记录与表现不改变物理的验收案例 |

确需A改现有文件时，B先冻结该文件并明确交接整个文件，A完成后再交回；不采用“上半段归B、下半段归A”。文件新增、改名、职责迁移和正式接线一起登记，避免实际依赖改变而所有权表仍过期。

## 先固定小接口，再平行开发

以下为拟议契约，尚未落成代码。S1只拆当前并行所必需的接口，不重写整个工程。

- 数据：玩法提供只读显示快照，例如稳定实体标识、当前/最大生命、生命等级、阵营、冷却/储能、阶段、货币、奖励进度和状态。A按数据画图，不能为显示另维护可独立扣血的钱包或生命。
- 事件：玩法发出有效受击、死亡、真实碰撞、发射、拾取、选卡、阶段/胜负等事件；载荷含必要的位置、强度、来源/整局版本。表现仅消费，不反向计算伤害或重复结算。
- requests：按钮/快捷操作提出`request_restart`、`request_choose`、`request_purchase`等请求；B的状态机再次校验状态、报价/版本、库存与余额。表现不能直接改`hp`、生成敌人或跳过阶段。
- 物理：绘制、粒子、换主题不改刚体质量、碰撞形状、层与掩码、冲量和速度规则；运动继续使用力/冲量，复位走物理状态接口。
- 兼容：先复用已有信号，再按需要包装；每次改变接口同时提供前后示例、受影响调用者、回归与迁移步骤。

## 阶段顺序与验收

| 阶段 | 工作与负责人 | 出口条件 |
| --- | --- | --- |
| S0：共同基线 | B确认本批Review/PR/merge的实际结果，用户审阅；两台电脑同步同一基线SHA，登记独立分支/目录与所有权 | 正式入口可运行；已有修改被保留；双方实际Godot版本一致；没有把旧分支SHA当新主线 |
| S1：必要拆分 | B从当前需要并行的一个actor或面板拆表现接点，与A对照数据/事件/requests；补物理隔离回归 | 只读契约明确，一个最小可替换表现例子能接通；既有物理/输入/奖励/重开回归通过 |
| S2：A样板与B实验室并行 | A重新提出战斗HUD＋奖励/休息面板样板；B做独立实验室和开发预设保存 | 用户看到并评价新样板；实验室与正式运行隔离；未确认视觉不批量替换 |
| S3：一种机制对照 | 先由用户选择一个机制并写目标/验收，再由B实现最小试验；A只在需要时做该试验反馈 | 记录基础配置与机制配置在同场景/种子下的差异、失败路径和真实试玩；没有擅自把候选清单都做完 |
| S4：集成验收 | B接线和回归、语义合并文档与重生成目录；独立审查者只读检查；用户作为owner最终审阅 | 规则、教程、用途/目录、自动检查与真人适用项有证据；明确未测项和下一次Git授权范围 |

实验室快捷键只在实验室生效，F5旧侧视、F6当前run和arena三靶场继续保留。开发参数保存为项目相对的开发预设，默认不写回正式资源、不自动覆盖正式入口；个人试验可先放忽略目录，共享开发预设另经Review。不得为了“方便对照”默认调慢正式运行速度，正常速度、全屏空白拖动和运动中冲量发射保持不变。

## A线：表现任务A1～A6

以下均为后续任务，不是本次文档已经实现的功能。A先给样板，B只做必要接线；用户确认方向后才扩到正式全套。

| 任务 | 范围及交付 | 验收与交给B的内容 |
| --- | --- | --- |
| A1：视觉方向与规范 | 新战斗画面、选卡/休息面板样板；色板、字体层级、间距、线宽、按钮状态和素材来源说明 | 用户明确评价新方向；1280×720及较小窗口可读；不用被否定的暖色样板默认定稿，交可编辑资源和尺寸规范 |
| A2：角色与场地辨识 | 主球、伙伴、三类敌人、首领、食物、障碍的独立表现样板；阵营/当前生命等级与预警区别 | 不只靠颜色，轮廓与标记可辨；生命数字和高低等级清楚；不改质量/碰撞形状/物理参数，交显示数据需求与表现组件 |
| A3：战斗HUD | 生命、储能/冷却、阶段、货币、击杀奖励进度；调试读数退到开发面板 | 受伤/回血/增上限/重开同步；按钮独占输入、空白穿透；3/4选卡与战斗HUD不遮挡，交所需只读快照和requests |
| A4：选择与流程面板 | 奖励、商店、事件、暂停、准备、胜败的统一组件与悬停/按下/禁用状态 | 状态和可行动作清楚，余额不足/满血/限购可理解；文案换行；不直接结算交易或跳状态，交报价/版本请求接口 |
| A5：碰撞、伤害与粒子 | 轻/重碰撞、有效伤害、无效接触、死亡、拾取、连锁、转场的分层表现 | 反馈对应实际事件，不用碰撞亮环冒充扣血；密集战斗限制遮挡/闪烁/粒子预算；关闭震动仍可读，交事件映射和预算 |
| A6：声音与整套一致性 | 多事件音组、UI/SFX层级与开关；密集连锁/受伤/确认的试听样例；与A1～A5合看 | 真机试听可区分、不刺耳、不过度重复；重要提示不被碰撞吞没；用户评价与设备记录完整；交音组资源和集成清单，不以调度测试代替音质 |

A1决定方向；A2～A4按已确认规范逐项推进；A5/A6可在对应事件契约稳定后并行制作。最终一致性检查涵盖真实战斗与流程面板，不能只看孤立静态图。若一个任务需要改B单写的现有actor/HUD/impact文件，仍走整文件交接或B接线。

## B线：实验室首版与后续

实验室是拟建的独立开发入口，不替换正式run。首版只用现有敌人和机制，目的是回答“为什么这次撞击有效/无效、哪个参数改善了手感”，不预先植入新玩法。以下八种夹具属于首版范围，可按小任务逐一完成，不能因写进表里就报告已经可用。

| 夹具 | 固定条件与要观察的问题 |
| --- | --- |
| 单敌 | 指定种类/生命、固定位置和发射向量；看速度门槛、伤害、击退及无效接触原因 |
| 怪群 | 固定数量、队形、种子；看穿群动量、密集接触、预算、清场时间 |
| 墙角 | 同一墙/斜挡板与固定起点；看反弹、角落卡住与实体碰撞，不偷偷改变正式墙形状 |
| 伙伴 | 固定伙伴数、初始不跟随，对照跟随/接力；看代数、激活/回收与障碍实体碰撞 |
| 范围 | 控制玩家与近战敌人的距离；看索敌、预警、有效范围与触碰伤害的实际边界 |
| 炮台 | 固定距离/朝向和弹预算；看射程、瞄准预警、弹轨迹及范围外不攻击 |
| 分裂 | 固定4/6生命族根与开关；看局部预警、安全延迟、代数、整族奖励与清波 |
| 首领 | 固定首领阶段和基础构筑；看模块、护甲、弱点、冲刺/震波与胜负清理 |

### 参数白名单与生效时机

开发面板只暴露明确映射到现有规则的参数，显示范围、单位、正式基准、试验值和生效时机。首版不提供任意`set(property, value)`输入框，不改`Engine.time_scale`，不把试验值自动写回正式`.tres`或actor场景。

| 白名单 | 首版建议生效规则 | 重置要求 |
| --- | --- | --- |
| 显示调试读数、事件日志、范围辅助线，试听音量/静音/震动 | 立即生效，仅实验室表现 | 重置可保留显示偏好，不改变战斗状态 |
| 发射冲量倍率、阻尼/摩擦、速度上限、受击续航，冷却/双发 | 下一次夹具重置后生效 | 从固定基准重算，清发射链/旧冷却和手势，避免半轮切换混淆结果 |
| 敌人类型、初始生命/数量/质量、追踪/攻击节奏、索敌/脉冲/炮台范围、弹速 | 下一次重建夹具后生效 | 旧实体/弹/预警必须清理，不给已在攻击中的敌人中途换规则 |
| 伤害速度门槛、接触去重间隔、伙伴数量/跟随/代数、构筑与分裂偏好 | 下一次夹具重置后生效 | 清战斗历史、二次撞击、临时攻击资格、分裂队列和奖励状态 |
| 固定种子、玩家/目标起点、发射方向与力度、墙角布局、首领夹具状态 | 下一次重建夹具后生效 | 起点复位走物理状态接口；等待复位完成才允许固定发射 |

首版统一采用“改值→显示待应用→重置生效”，仅表现开关即时生效；后续若确需热调某个物理参数，单独写清安全边界并补测试，不让两个生效模式混在一起。

### 固定发射、读数与拒伤日志

固定发射必须经过正式发射接口，在统一起点、种子、方向、力度和初始构筑下给一次真实冲量；不能用直接设置速度代替，不能绕过阻塞/冷却/复位检查。首版“重复一次”是复位后再发射相同请求，保证前后可比较；完整输入录制和自动批量回放留后续。

读数至少包含：实体/整局标识、当前速度与接触相对速度、发射链/代数、发射是否可用和冷却、目标当前/最大生命、本次实际伤害、当前击退/受击停顿状态、有效命中/无效接触次数、当前活敌/预警/危险弹、清场用时。物理观测须标明取样时机，不把显示帧速度冒充接触瞬间速度。

拒伤原因在逻辑判定处记录，首版分清：无攻击资格、正在复位/旧局事件、目标不可受伤或已死、速度不足、同一配对冷却、敌人投射物已命中过/资格耗尽、玩家无敌/非有效攻击、超出实际攻击范围。日志带源/目标ID、战斗时间、链与世代、速度/阈值、判定结果；使用有界环形缓冲，同原因可合并计数，默认只在实验室开启。不能为了记日志再执行一次伤害判定或改变去重顺序；未拿到原因时标明未知，不用视觉猜测。

### 预设、复现记录与快捷键

首版提供保存/加载开发预设与恢复夹具默认：保存schema版本、基线SHA、夹具ID、种子、白名单参数、初始构筑和固定发射请求；加载先校验版本与字段、显示偏差，再重建夹具，不覆盖正式默认。个人预设放忽略目录；需跨电脑共享时转成经Review的项目相对开发资源，不含本机绝对路径。复现记录最少包含主机/Godot版本、基线/分支、预设标识、步骤、预期/实际、读数/日志片段和截图/录音链接、未测项。

后续再评估批量参数扫描、输入录制/回放、曲线/时间线和统计导出；只有首版单次复现可靠后才扩展，不把完整分析平台算作先决条件。

建议快捷键仅在实验室：`1～8`切八种夹具，`R`重置并应用待生效值，`T`固定发射，`L`显隐读数/日志，`Ctrl+S`保存开发预设，`Ctrl+O`选择加载预设。文本框/选项框正在编辑时不触发；实际按键冲突在实现时检查。这是建议映射，当前没有实现，也不覆盖编辑器F5/F6或向正式run注册全局输入。实验室与正式运行都默认正常速度。

## 三种机制候选：等用户选一个

| 候选 | 最小原型要回答的问题 | 对照与边界 |
| --- | --- | --- |
| 借墙蓄能 | 真实撞墙是否能形成“找角度蓄能后进攻”的选择 | 同夹具对照有/无蓄能；明确触发墙、速度门槛、上限与消耗，不让擦墙无限充能 |
| 方向弱点 | 观察朝向并从侧/后方撞击是否比直冲更有决策价值 | 同敌人与冲量对照不同接触方向；弱点提示可读，不让绘制朝向与真实判定脱节 |
| 交互场地 | 有限场地机关是否能服务碰撞接力，而不是只增加噪声 | 只做一种可解释交互，与无机关基线对照；机制运动仍靠力/冲量，避免自动伤害淹没发射决策 |

这三项仅是命名候选，用户尚未选择，也未授权三项全做。S3只在用户选定后写一项最小规格/验收和复现夹具，再实现一个原型；是否进入正式run依据真实体验和后续明确授权决定。

## 两台电脑、分支与共享文档

每次新会话/切换电脑先查实际主机名、OS、用户、工作目录，按需核验Git、Godot实际路径与版本。两台电脑各用独立checkout，不共享同一个正在编辑的工作目录，不复用另一台机器的绝对路径、凭据或插件事实。固定Godot4.7.1 stable标准版、Compatibility。

两人从同一个已验证SHA各开分支，遵循`CONTRIBUTING.md`的`feat/`前缀，例如`feat/presentation-sample`与`feat/gameplay-lab`；修错/文档任务分别使用既有`fix/`、`docs/`约定。示例名不代表已创建分支。现有本机未提交修改先保护，不能为对齐基线执行破坏性重置。

各分支可同步更新自己涉及的教程、`docs/STATUS.md`和`docs/file_purposes.json`，也应生成本分支的`FILE_MAP.md`用于检查；集成时由B逐条语义合并用途与状态，重新生成`FILE_MAP.md`，不手工拼树、不直接选ours/theirs丢掉另一方内容。共享文档不是绕过同文件写入约束的理由：同一checkout中仍由登记的单一写入者收集两方内容；独立分支产生的文档差异在集成时合并。

## 交接、Review与完成判据

每个小任务的Issue或PR记录目标、验收、文件清单、负责人、教程与验证；尚未授权线上记录时保存在本地任务文档，不擅自建Issue。交接至少给出基线SHA、分支、修改文件、接口/参数变化、实跑命令及结果、真人观察、未测项和所需接线。使用[教程020的模板](../tutorials/020-parallel-workflow.md)。

开发中可局部检查；准备进入Git阶段才由开发者发起最终Review。A/B自己的检查标明自查，独立Review交未参与实现的人或Agent。测试通过不能替代音质试听、视觉样板评价和真人手感。发现阻塞后只修复并复测受影响范围，独立审查者确认，再由用户作为owner审阅和按当次授权完成Git动作。

完成本计划的文档不等于完成S1～S4。当前可以核对的是角色、文件边界、任务先后和授权是否明确；后续实现分别以真实代码、测试和试玩作为完成证据。最终交付不维护第二套大型Agent日志，事实来源仍是仓库和获授权的GitHub记录。
